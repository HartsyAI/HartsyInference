# Vulkan bring-up status

Which models have actually been run on the Vulkan backend, and what happened. One row per model attempted;
anything not attempted says so rather than being inferred from op coverage, which over-predicts failure — most of
the ops Vulkan lacks have a working host fallback, so a missing override usually costs speed, not correctness.

Regenerated by `tests/vulkan-smoke-matrix.sh`. Numbers live in the
[Vulkan scoreboard](../../benchmarks/scoreboards/VULKAN.md), verification evidence in
[PARITY_VERIFICATION.md](PARITY_VERIFICATION.md), open bring-up work in [ROADMAP.md](ROADMAP.md) §3. This file
holds the verdict and the reason only.

**Reading a verdict.** `runs` means the command completed and produced output of the expected kind. It is **not**
a quality verdict — whether the output matches CUDA is a separate question, answered per model in the parity doc.
`crashes` means it failed on Vulkan where CUDA succeeds. `incomplete` means the model's companion weights are
absent locally, so the run says nothing about the backend. `untested` means exactly that.

confirmed run, and the two attempts failed on absent weights rather than on the backend.

## What this does not establish

**DeepSeek-V4.1-Flash primitives (PR 24b).** The MoE, HC, latent-attention, quantizer and recipe-dequant shaders are parity-tested against the
CPU reference on an RTX 3060 through Vulkan only. No AMD hardware evidence has been collected, so none of it is certified on AMD, and nothing
is wired into a model. The expert cache is host-staged with no streaming cache, and native block-scaled GEMM is Unsupported on Vulkan.

**Nothing about AMD or Intel.** Every row is NVIDIA-Vulkan on an RTX 4090. No AMD or Intel GPU exists on this
machine; llvmpipe covers small-subgroup correctness and is not evidence about either vendor's driver. That is
ROADMAP §3's remaining hardware item.

**Not output parity.** SDXL on Vulkan and on CUDA produce different images from the same seed, and the gap grows
with step count. The components isolated so far are clean — the batched convolution is bit-identical to
per-image, GroupNorm/Silu/Linear/SDPA are bitwise batch-independent, `CfgEulerStep` holds at ~1e-7 across twenty
in-place steps, and TF32 was ruled out by re-running CUDA with `numerics.noTf32` for a 0.0001 SSIM difference.
For calibration: a real precision change *inside* CUDA costs ~2% SSIM over 20 steps at this guidance, while the
cross-backend gap is ~44%. So the residual is larger than rounding and remains unexplained; attention and the
GEMM dtype path are the untested suspects.

**Not speed.** A `runs` verdict says nothing about how long it took relative to CUDA; the scoreboard carries that.
