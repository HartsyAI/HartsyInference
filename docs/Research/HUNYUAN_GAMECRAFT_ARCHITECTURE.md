## Summary

Hunyuan-GameCraft 1.0 (Tencent, paper arXiv 2506.17201, code + weights released 2025-08-14) is an **action-conditioned, image-and-text-prompted, autoregressive long-form video diffusion model** built for interactive game-style footage. The user supplies (a) a reference first frame, (b) a text prompt, (c) a sequence of discrete keyboard actions from the set `{w, a, s, d}` plus mouse signals each annotated with an action-speed scalar in `[0, 3]`. The model emits 33-frame, **720p (704×1216)**, 25 fps clips that can be chained autoregressively into arbitrarily long video by feeding prior frames as history conditioning.

The denoiser is a **drop-in re-instantiation of the HunyuanVideo MM-DiT transformer** (Tencent's 13B text-to-video model), retrained end-to-end on a corpus of >1 M gameplay recordings spanning 100+ AAA titles plus a fine-tuning pass on synthetic, precisely-annotated action–video pairs. Backbone config: `hidden_size=3072`, `num_heads=24` (`head_dim=128`), `depth_double_blocks=19`, `depth_single_blocks=38`, `mlp_ratio=4.0`, RMSNorm Q/K, 3D RoPE with `rope_dim_list=[16, 56, 56]` (t, h, w summing to 128 = head_dim), patch size `[1, 2, 2]`, latent in/out channels = 16. This puts the GameCraft transformer at the same ≈13 B-parameter scale as HunyuanVideo. (The author config `depth_double=19 / single=38` is one block fewer per stream than vanilla `HunyuanVideoTransformer3DModel` (20/40) — see § Differences.)

Two novel architectural pieces sit *on top of* that backbone:

- **CameraNet** — a lightweight 6-channel-in convolutional action encoder that turns the discrete `(w/a/s/d/mouse, speed)` sequence into a **Plücker-coordinate camera-ray map** (6 channels per pixel), spatially down-shuffles 8× via `PixelUnshuffle`, applies two `Conv2d → GroupNorm → ReLU` blocks with temporal pooling between them, projects to 16 channels, and patch-embeds into the same 3072-dim token space as the latent — then **adds** those tokens, scaled by a learnable per-channel coefficient initialized to zero, to the noisy latent tokens after patchify. Token-addition (not cross-attention) is the fusion mechanism.
- **Hybrid history conditioning** — every input latent gets a `+1` extra channel (`6` channels total post-cat instead of the 16-channel latent expectation, see § Channel layout for the actual concat ordering) that is a per-frame binary mask: `1` on frames that are history (the previous clip's clean latents, copied into the input), `0` on frames that are noisy / to-be-predicted. During training Tencent samples three regimes: 70 % single-historical-clip continuation, 5 % multiple historical clips, 25 % single reference-frame (first-frame image-to-video). At inference, autoregressive long-form rollout always uses the single-historical-clip path.

Text conditioning uses HunyuanVideo's dual encoder — **Llava-Llama-3-8B-v1.1** as the primary high-dim sequence encoder (≈4096-dim hidden, passed through a TokenRefiner) and **CLIP-ViT-Large-Patch14** as the pooled global encoder (768-dim). VAE is HunyuanVideo's **3D causal VAE** (`884-16c-hy0801`): 16 latent channels, 8× spatial compression, 4× temporal compression, causal-conv3d. Scheduler is **FlowMatchDiscreteScheduler** (`num_train_timesteps=1000`, `shift=5.0` at inference, `reverse=true`, Euler solver). CFG at scale 2.0 over 50 steps for the base model; a **Phased Consistency Model (PCM)** distilled variant runs in **8 steps with CFG=1.0** for ≈10-20× speedup, hitting 6.6 fps on the reference 8×H20 setup.

For HartsyInference: the **transformer code can be ≈98 % shared with a future HunyuanVideo pipeline** (only the input-channel count and the CameraNet attachment differ). The hard new work is (a) Plücker-ray generation from `(w/a/s/d, speed)` sequences, (b) the 3D causal VAE decoder, (c) Llava-Llama-3-8B text-encoder inference (likely shared with dotLLM via the existing Llama backbone), and (d) a **`.pt` (PyTorch pickle) loader** — the weights ship only as `mp_rank_00_model_states.pt` (30.2 GB) and `mp_rank_00_model_states_distill.pt` (30.2 GB), not safetensors. See § File tree warning.

>
> 1. **Ship a one-off Python conversion script** (`tools/convert_gamecraft_pt_to_safetensors.py`) that the user runs once, post-download, to produce a `model.safetensors` + `model.safetensors.index.json`. > 2. **Implement a minimal `.pt` reader in C#.** PyTorch `.pt` is a ZIP container holding a Pickle stream that references `data/N` blob files (raw little-endian tensor bytes) plus a `data.pkl` index. A safe-subset pickle parser (handling only the ops PyTorch emits: `torch._utils._rebuild_tensor_v2`, `OrderedDict`, `collections.OrderedDict`, `torch.BFloat16Storage`, `torch.HalfStorage`, etc.) is ≈600 LOC of C# and avoids the pure-Python conversion dependency. **This is the architecturally cleaner option** but adds maintenance surface for a single license-restricted model. Recommend option 1 unless we end up needing `.pt` support for other models too.

The HF detection bot reports the `.pt` files contain: `torch._utils._rebuild_tensor_v2`, `OrderedDict`, and `torch.BFloat16Storage`. Both `.pt` files are flat state dicts (key → bf16 tensor), not nested `Module` pickles.

Forward signature (verbatim):

```python
def forward(self, x, t,
    text_states=None, text_mask=None,        # Llava-Llama-3-8B sequence
    text_states_2=None,                       # CLIP-L pooled (768)
    freqs_cos=None, freqs_sin=None,           # precomputed 3D RoPE freqs

```

Block layout follows the FLUX / HunyuanVideo recipe: **dual-stream → single-stream**.

- **DoubleStreamBlock** (×19) — two parallel residual streams (image-tokens, text-tokens). Each stream has its own pre-attention RMSNorm + DiT-style 6-factor modulation (`shift_msa, scale_msa, gate_msa, shift_mlp, scale_mlp, gate_mlp` from timestep + global text). Attention is **joint**: streams are concatenated along the sequence axis, run through one shared scaled-dot-product attention with 3D RoPE applied only to image tokens, then split back. Each stream has its own post-attention RMSNorm + GeGLU-tanh MLP at `mlp_ratio=4`.
- **SingleStreamBlock** (×38) — image and text tokens are concatenated permanently and processed as a single stream. Each block has one **parallel linear** projection (`Linear → QKV + MLP_up`), one RMSNorm-Q + RMSNorm-K, one joint attention, GeGLU-tanh, and one merged output `Linear → hidden_size`. Modulation has 3 factors (`shift, scale, gate`). This is identical to FLUX's `single_stream_block`.

Total parameter count: per the paper, "9.0 B attention+MLP / 12.5 B total" — the 12.5 B figure matches HunyuanVideo's "≈13 B" headline once you account for the missing 1-double / 2-single blocks and add CameraNet (~tens of M). Activation bf16; checkpoint also bf16.

### 3. Action encoder — `CameraNet`

Defined in `hymm_sp/modules/cameranet.py`. Pipeline (in evaluation order on input `(B, T, C_in=6, H, W)`):

1. **`PixelUnshuffle(downscale_coef=8)`** — spatial 8× downshuffle: `(B, T, 6, H, W) → (B, T, 6·64=384, H/8, W/8)`. This matches the VAE's 8× spatial compression so camera tokens align with latent tokens.
2. **`Encode_first` block** = `Conv2d(384 → 192, k=1) → GroupNorm(num_groups=2, num_channels=192) → ReLU`.
3. **Temporal compression** (first pass) — custom pooling that preserves initial frames while reducing frame count (matches the VAE's 4× temporal compression on non-first frames, so output frame count = `(T - 1) / 4 + 1`).
4. **`Encode_second` block** = `Conv2d(192 → 96, k=1) → GroupNorm(2, 96) → ReLU`.
5. **Temporal compression** (second pass) — applied if `camera_down_coef` indicates further reduction (in the default config, only one temporal pass is active to match the 4× VAE compression).
6. **Final projection** = `Conv2d(96 → out_channels=16, k=1)` with **zero-init weights** so the network starts as an identity skip (no impact on early training).
7. **`PatchEmbed(patch_size=[1, 2, 2], in_channels=16, hidden_size=3072)`** — same patchifier the noisy latent uses, projecting to the DiT's 3072-dim token space.
8. **Learnable per-channel scaling coefficient** — multiplied onto the camera tokens before addition. Initialized to a small value so CameraNet starts as near-zero.

**Fusion with the denoiser:** in the DiT `forward`, after the noisy latent + history + ref is patchified into image tokens `x_img ∈ (B, L_img, 3072)`, the `cam_latents` tensor produced by CameraNet (also of shape `(B, L_img, 3072)`) is **added** to `x_img` before entering block 0. This is "token addition" in the paper's terminology — chosen over cross-attention because it adds no per-block compute and no extra parameters per block.

**Input to CameraNet** is **not** raw `(w/a/s/d, speed)` symbols; it is a **6-channel Plücker-coordinate per-pixel camera-ray map**. See § 5 for the action → Plücker conversion. The 6 channels encode the per-pixel ray as the concatenation of the 3D ray direction (3 channels) and the moment vector (3 channels, computed as cross-product of ray origin × direction) — the standard Plücker line representation used by CameraCtrl, MotionCtrl, and similar camera-controlled video models.

### 4. Latent channel layout (history + reference cat)

The denoiser's nominal `in_channels = 16` (VAE latent channels). Hybrid history conditioning is implemented via **concatenation along the channel axis** at the input to the patchify layer:

- **Noisy target latent** — 16 channels, shape `(B, T_lat, 16, H_lat, W_lat)` where `T_lat = (33 - 1)/4 + 1 = 9`, `H_lat = 704/8 = 88`, `W_lat = 1216/8 = 152`.
- **Reference / history latent** — 16 channels, same spatial shape. Filled with the clean VAE-encoded latent of either (a) the previous chunk's last frames (autoregressive rollout), or (b) the reference first frame (image-to-video bootstrap), or (c) several previous chunks (mode 2 in training).
- **Mask channel** — 1 channel of binary 0/1 broadcast across `(H_lat, W_lat)` (or replicated per-pixel; same effect), where each `T_lat`-th frame is `1` if that frame is history, `0` if it's to be predicted.

The cat is `[noisy, ref/history, mask]` along channel dim → **33 channels into patchify** (≠ 16). The diffusers-equivalent `HunyuanVideoTransformer3DModel(in_channels=16, out_channels=16)` will not load this config directly; the patchify input projection's first dim must be 33 in the GameCraft checkpoint. (Likely tensor key: `img_in.proj.weight` of shape `[3072, 33, 1, 2, 2]` after patchify dim flatten — to verify, see Open Questions.)

Training mode breakdown (from the paper):

| Mode | Probability | Description |
|---|---|---|
| Single historical clip | 0.70 | Previous 33-frame clip's last `N_hist` frames in the ref/history latent, mask=1 on those slots. |
| Multiple historical clips | 0.05 | Several non-contiguous prior chunks (rarely used at inference). |
| Single reference frame | 0.25 | Only the first frame (the user-provided image) in the ref/history latent, mask=1 on that one frame. This is the "image-to-video bootstrap" mode used at inference for the first chunk. |

At inference autoregressive rollout: chunk 0 uses mode 3 (reference frame from user image); chunks 1..N use mode 1 (previous chunk's tail as history).

### 5. Action → Plücker conversion (`ActionToPoseFromID`)

Located in `hymm_sp/data_kits/`. The continuous action space defined in the paper is

> 𝒜 = {(d_trans, d_rot, α, β)}

where `d_trans, d_rot ∈ S²` (unit vectors on the 2-sphere) give translation and rotation direction, `α ∈ [0, v_max]` is translation speed, and `β ∈ [0, ω_max]` is rotation speed.

CLI inputs:

- `--action-list w s d a` (one symbol per chunk; each symbol corresponds to **one 33-frame chunk @ 25 fps ≈ 1.32 s**).
- `--action-speed-list 0.2 0.2 0.2 0.2` (one float per chunk in **[0, 3]**; 0 = stationary, 0.2 = comfortable walk pace, 3 = sprint).

Action → continuous mapping (inferred from `ActionToPoseFromID` and the paper's Eq. 1):

| Symbol | `d_trans` | `d_rot` (Euler) | Comment |
|---|---|---|---|
| `w` | `+z` (forward) | 0 | Walk forward. |
| `s` | `-z` (back) | 0 | Walk backward. |
| `a` | `-x` (strafe-left) | 0 | Strafe left. (No yaw — pure translation in keyboard-only mode.) |
| `d` | `+x` (strafe-right) | 0 | Strafe right. |
| (mouse symbols, present in `ActionToPoseFromID` but not exposed in default CLI) | — | yaw / pitch | Mouse_up/down/left/right map to camera rotation around pitch/yaw. |

Inside one chunk, the action is held constant and integrated over 33 frames to produce a **trajectory of 33 camera poses** (position + quaternion). The trajectory is then **lifted to Plücker ray maps** at the target resolution:

1. For each frame `f ∈ [0, 33)`, compute the 4×4 camera-to-world pose `T_f` from cumulative translation `α · d_trans · (f / fps)` and cumulative rotation `Rot(β · d_rot · (f / fps))`.
2. For each pixel `(u, v)`, compute the camera-space ray direction from the pinhole intrinsics, transform to world space via `T_f`, normalize → `d ∈ ℝ³`.
3. Compute the moment vector `m = origin × d` where `origin = T_f.translation`.
4. The Plücker map is `(d, m) ∈ ℝ⁶` per pixel → tensor shape `(33, 6, 704, 1216)`.

This Plücker map is what CameraNet ingests as `(B, T=33, C=6, H=704, W=1216)`. Note that the per-pixel encoding makes camera control **dense and geometrically grounded**, not a one-hot action token — this is the key reason GameCraft can interpolate smoothly between actions.

The paper also notes the action speed `α ∈ [0, 3]` is interpreted as "displacement distance per chunk in world units," so a speed of `0.2 w` advances the camera ≈0.2 m forward over the chunk; chaining four `0.2 w` actions over four chunks (132 frames total) walks ≈0.8 m forward.

### 6. Text encoders

GameCraft uses **HunyuanVideo's dual-encoder text stack unchanged**:

- **Primary: Llava-Llama-3-8B v1.1** (`stdmodels/llava-llama-3-8b-v1_1-transformers/`).
    - Architecture: standard Llama-3 8B decoder (32 layers, hidden 4096, 32 heads, 8 KV heads (GQA-4), FFN 14336, RoPE θ=500000, vocab 128256, RMSNorm, SwiGLU).
    - The Llava variant adds a frozen CLIP-ViT-Large vision tower and an `mm_projector` MLP — at GameCraft inference only the **language tower** is used, on text prompts only. Tencent applies a *prompt template* (the diffusers default `'template'` string starting `"<|start_header_id|>system<|end_header_id|>\n\nDescribe the video..."`) and `crop_start=95` to discard the system-prompt portion of the resulting hidden states.
    - Output: per-token hidden states of shape `(B, L_text, 4096)`, attention mask `(B, L_text)`. `max_sequence_length = 256` by default.
    - Passed through the DiT's `TokenRefiner` (2 self-attention layers, 3072-dim, same as HunyuanVideo) before entering DoubleStreamBlocks.
- **Pooled: CLIP-ViT-Large-Patch14** (`stdmodels/openai_clip-vit-large-patch14/`).
    - Standard OpenAI CLIP-L (12-layer Transformer, hidden 768, 12 heads, vocab 49408, context 77).
    - Output: pooled `(B, 768)` text embedding (the EOS-token's hidden state after final projection). Combined with timestep into the global modulation vector via a `CombinedTimestepTextProjEmbeddings` MLP.

Both encoders are **frozen**; GameCraft does not fine-tune them. The Llava-Llama path is the same one `dotLLM` already implements for Llama-3-8B, so the bulk of text-encoder code is shareable.

### 7. VAE — `884-16c-hy0801`

The string `884-16c-hy0801` is HunyuanVideo's naming convention: **8×8 spatial, 4× temporal, 16 channels, version "hy0801"** (HunyuanVideo, August 2024). Loaded via `stdmodels/vae_3d/hyvae/`.

- Latent channels: **16** (so the 33-frame, 704×1216 RGB clip → 9-frame, 88×152, 16-channel latent).
- Spatial compression: **8×8** (`H/8`, `W/8`).
- Temporal compression: **4×** (causal: `T_lat = (T_pixel - 1)/4 + 1`, so 33 → 9, 65 → 17, 129 → 33).
- Architecture: **3D causal VAE** with CausalConv3d (only past+present, no lookahead) so encode/decode can be streamed frame-by-frame.
- Standard VAE pieces: ResnetBlock3D + Downsample3D in encoder, ResnetBlock3D + Upsample3D in decoder, SpatialNorm + 3D self-attention at the bottleneck.
- Trained with KL loss + LPIPS + adversarial loss (per HunyuanVideo paper).
- VAE dtype at inference: fp16 per the recommended diffusers table.
- Supports tiling + slicing for low-VRAM (cf. `enable_vae_tiling()` in diffusers' equivalent).

The VAE is fully reusable as-is for any future HunyuanVideo pipeline in HartsyInference.

### 8. Scheduler — `FlowMatchDiscreteScheduler`

Defined in `hymm_sp/diffusion/schedulers/scheduling_flow_match_discrete.py`. Constructor defaults:

```python
class FlowMatchDiscreteScheduler(SchedulerMixin, ConfigMixin):
    num_train_timesteps: int = 1000
    shift: float = 1.0          # overridden at inference: 5.0 (flow-shift-eval-video)
    reverse: bool = True
    solver: str = "euler"
    n_tokens: Optional[int] = None
```

Setup logic:

1. `sigmas = torch.linspace(1, 0, num_train_timesteps + 1)` — linearly spaced 1 → 0 over 1001 points.
2. Apply **SD3-style time shift** at inference: `t_shifted = (shift · t) / (1 + (shift − 1) · t)`. With `shift=5.0` this pushes sigmas toward higher noise levels (= more denoising steps spent on the noisy end), matching HunyuanVideo's recommended 5.0–7.0 for video.
3. `timesteps = (sigmas[:-1] * num_train_timesteps).float()` — discrete timestep values fed to the model.

Step (Euler): `prev_sample = sample + model_output * dt` where `dt = sigmas[i+1] - sigmas[i]`. `reverse=true` reverses the sigma schedule so we step from `t=1` (pure noise) down to `t=0` (clean).

**Inference configurations:**

| Config | `infer-steps` | `cfg-scale` | `flow-shift-eval-video` | Checkpoint |
|---|---|---|---|---|
| Base | 50 | 2.0 | 5.0 | `mp_rank_00_model_states.pt` |
| Distilled (PCM) | 8 | 1.0 | 5.0 | `mp_rank_00_model_states_distill.pt` |

The distilled model is a **Phased Consistency Model** with **CFG Distillation**: the consistency objective makes 8-step trajectory faithful to the 50-step base, and CFG distillation folds the implicit-CFG behaviour into the unconditional pass so `cfg-scale=1.0` (i.e. only one model forward per step) reproduces what would otherwise need two forwards at `cfg-scale=2.0`. End-to-end speedup: **10–20×**, hitting **6.6 fps** generation throughput on the reference 8×H20 hardware setup. CFG branch at base: standard cond/uncond two-pass with linear interpolation `pred = uncond + scale * (cond − uncond)`.

## Data Layouts / Formats

### Checkpoint format

- **Container**: PyTorch `.pt` (pickle) — *not* safetensors. ZIP archive containing `data.pkl` (a Python pickle stream calling `torch._utils._rebuild_tensor_v2`) plus `data/0`, `data/1`, ... blob files holding raw bf16 tensor bytes in little-endian. `OrderedDict` keys map tensor names → reconstituted tensors.
- **Layout**: flat state dict, **not** a nested `nn.Module` pickle. Loading is `state_dict = torch.load(path, map_location='cpu')`, then `model.load_state_dict(state_dict)`.
- **Model-parallel naming**: `mp_rank_00_` indicates DeepSpeed Megatron-style tensor-parallel rank 0. Current release ships only rank 0 (i.e. the model is materially single-GPU-shape; sequence parallelism is done dynamically at runtime via the `_sp` package). Future Tencent releases could in principle ship `mp_rank_01_...` etc.
- **Dtype**: bf16 throughout, including CameraNet.
- **Suggested key naming** (to verify by dumping with `torch.load` + `.keys()`):
    - `img_in.proj.weight`, `img_in.proj.bias` — patchify input projection (shape `[3072, 33, 1, 2, 2]` after factoring patch into channel — flatten gives 33*1*2*2 = 132 → likely `[3072, 132]` actual storage).
    - `txt_in.proj.weight`, `txt_in.proj.bias` — Llava-Llama → 3072 input projection.
    - `txt_in.individual_token_refiner.blocks.{0,1}.*` — TokenRefiner self-attn + FFN.
    - `time_in.mlp.{0,2}.{weight,bias}`, `vector_in.{...}` — timestep + CLIP-L embedding stacks.
    - `double_blocks.{0..18}.img_attn_qkv.{weight,bias}` / `.img_attn_proj.*` / `.img_mlp.{0,2}.*` / `.img_mod.lin.*` / `.img_norm1.*` / `.img_norm2.*` (similarly `.txt_*`).
    - `single_blocks.{0..37}.linear1.{weight,bias}`, `.linear2.{weight,bias}`, `.modulation.lin.*`, `.norm.*`, `.q_norm.scale`, `.k_norm.scale`.
    - `final_layer.linear.{weight,bias}`, `.adaLN_modulation.{1}.{weight,bias}`.
    - `camera_in.encode_first.{0,1}.{weight,bias}`, `camera_in.encode_second.{...}`, `camera_in.final_proj.{weight,bias}`, `camera_in.patch_embed.proj.{weight,bias}`, `camera_in.scale` — the learnable per-channel scale.

### Plücker camera-ray map

- Shape `(T=33, C=6, H=704, W=1216)`, fp32.
- Channels `[0..2]` = ray direction `d ∈ ℝ³`, normalized.
- Channels `[3..5]` = moment `m = origin × d ∈ ℝ³`.
- Origin: world-space camera position at frame `f` derived from cumulative `(d_trans, α)` integration.
- Camera intrinsics: pinhole; focal length implied by `(H, W) = (704, 1216)` and a fixed FOV (paper does not state the exact FOV — likely 60°; see Open Questions).

### Mask channel

- Shape `(B, T_lat=9, 1, H_lat=88, W_lat=152)`, fp32 in `{0.0, 1.0}` (not bf16, to avoid quantisation jitter in modulation downstream).
- `1` = history (clean reference latent), `0` = noise target.
- Broadcast vs per-pixel: in practice broadcast across `(H_lat, W_lat)` because a whole latent frame is either history-or-target.

### Latent input concatenation order

`x = cat([noisy_latent (B,9,16,88,152), ref_history_latent (B,9,16,88,152), mask (B,9,1,88,152)], dim=2)` → `(B, 9, 33, 88, 152)` → patchify to `(B, 9*44*76, 3072) = (B, 30096, 3072)`.

CameraNet output is added on top: `x_tokens += scale * cameranet(plucker_map)`.

## Algorithm Steps

### Single-chunk inference (no history; first chunk)

1. **Inputs**: reference image `I_ref` (H, W, 3), text prompt `p`, actions `[a_0]` with speeds `[s_0]`. Optional negative prompt `p_neg`.
2. **VAE-encode reference**: `z_ref = vae.encode(I_ref.unsqueeze(time)).latent` → `(1, 1, 16, 88, 152)`. Pad/repeat to `(1, 9, 16, 88, 152)`.
3. **Mask**: `mask` is `(1, 9, 1, 88, 152)` with `mask[:, 0] = 1, mask[:, 1:] = 0` (only frame 0 is "history").
4. **Encode prompt**: `t_llama, t_llama_mask = LlavaLlamaText(p, template, crop_start=95, max_len=256)`; `t_clip = CLIPText(p).pooler_output`. (And similarly for `p_neg` for CFG.)
5. **Build Plücker map**: `pl = ActionToPlucker(a_0, s_0, fps=25, n_frames=33, H=704, W=1216)` → `(1, 33, 6, 704, 1216)`.
6. **Setup scheduler**: `sigmas = FlowMatchDiscreteScheduler(shift=5.0).set_timesteps(50, reverse=True)` → 50 sigma values from 1.0 → 0.0 (shifted).
7. **Initial noise**: `z = torch.randn(1, 9, 16, 88, 152, dtype=bf16) * sigmas[0]`.
8. **Precompute RoPE**: `freqs_cos, freqs_sin = compute_3d_rope(rope_dim_list=[16,56,56], T_lat=9, H_lat=44, W_lat=76, rope_theta_per_axis=...)`.
9. **For each step `i ∈ [0, 50)`**:
    a. `x = cat([z, z_ref, mask], dim=2)`. Patchify → 30096 tokens.
    b. `cam_tokens = CameraNet(pl)` (computed once, cached across steps).
    c. `x += scale * cam_tokens`.
    d. `t_emb = TimestepEmb(sigmas[i] * 1000) + CLIPProj(t_clip)`.
    e. `txt_tokens = TokenRefiner(LlavaProj(t_llama), t_emb)`.
    f. **Conditional forward**: `v_cond = DiT(x, t_emb, txt_tokens, t_llama_mask, freqs_cos, freqs_sin)` → `(1, 30096, 3072)` → un-patchify → `(1, 9, 16, 88, 152)`.
    g. **Unconditional forward** (CFG): repeat (e)+(f) with `t_neg` instead of `t_llama` → `v_uncond`.
    h. `v = v_uncond + 2.0 * (v_cond − v_uncond)`.
    i. `dt = sigmas[i+1] − sigmas[i]`. `z = z + v * dt`. (Euler.)
10. **VAE-decode**: `frames = vae.decode(z)` → `(1, 33, 3, 704, 1216)`. Clamp, scale to `[0, 255]`, write video at 25 fps.

For the **distilled checkpoint**: same flow with `num_inference_steps=8`, `cfg-scale=1.0` (skip step g entirely — only one forward per step).

### Autoregressive long-form rollout (chunks N>0)

Chunks 1..N reuse steps 1–10 with two changes at step 2 and 3:

- `z_ref` is the VAE-encoded **last `N_hist` frames of the previous chunk's decoded output** (typically `N_hist = 33`, i.e. the whole previous chunk re-encoded; or just the last 1–8 frames for memory).
- `mask` is `1` on the `N_hist`/4-rounded latent slots corresponding to history, `0` on the rest.

The reference image plays no further role after chunk 0. Action symbol `a_N` and speed `s_N` come from the user's action list for chunk `N`.

### Training (informational only — not in HartsyInference scope)

- Phased consistency distillation (PCM) trains the 8-step student to match the 50-step teacher's trajectory at log-spaced phase boundaries (typically 4 phases over the 50-step trajectory).
- CFG distillation folds the implicit dual-pass CFG into a single forward by training the student under text-conditioning with the teacher's CFG-applied prediction as target.
- Full-parameter training (not LoRA) on 192× H20 GPUs, batch 48. Mixed precision bf16.

## Differences Between Implementations

1. **Backbone block counts vs HunyuanVideo base.** GameCraft's `HYVideoDiffusionTransformer` defaults to `depth_double=19, depth_single=38`, while diffusers' `HunyuanVideoTransformer3DModel` defaults to `num_layers=20, num_single_layers=40`. Tencent likely trimmed one dual + two single blocks to spend the parameter budget on (a) CameraNet, (b) the wider 33-channel patchify input, (c) the extra training compute for hybrid history. **A diffusers-style loader will not load GameCraft weights without explicitly overriding these depths.**
2. **`in_channels` mismatch.** HunyuanVideo expects `in_channels=16`. GameCraft cats noisy + ref + mask = **33**. The patchify projection's first conv weight differs in shape. (Implementers must construct the backbone with `in_channels=33`, not 16.)
3. **`guidance_embed`.** Vanilla HunyuanVideo uses CFG-distilled embedded guidance (`guidance_embed=True`, accepting a `guidance` tensor as input). GameCraft uses **raw two-pass CFG** at base (`cfg-scale=2.0`) and one-pass at distilled (`cfg-scale=1.0`); the `guidance` argument is unused.
4. **Distilled variant is PCM, not Hyper-SD or LCM.** PCM (Phased Consistency Model) has different boundary-step training than the LCM family. At inference both run as straight `step` calls on a Euler-flow scheduler — no special PCM-specific sampler. So the HartsyInference scheduler code is identical between base and distilled; only `num_inference_steps` and `cfg-scale` change.
5. **CameraNet has zero-init final projection + zero-init scale.** Means a freshly-constructed CameraNet contributes nothing — useful for sanity-checking the rest of the pipeline before loading CameraNet weights. (Equivalently: if CameraNet weights fail to load, the model degrades to a text-only HunyuanVideo-like behaviour rather than producing garbage.)
6. **Single-stream-block modulation.** GameCraft's `SingleStreamBlock` uses **3-factor modulation** (`shift, scale, gate`) on a single concatenated stream, where the equivalent FLUX/HunyuanVideo block also uses 3-factor — confirm by tensor key. The double-stream block uses 6-factor per stream (12 total).
7. **`flow-shift-eval-video=5.0` is hardcoded for the 720p / 33-frame regime.** Lower shift values (e.g. 3.0) are used in HunyuanVideo for 540p; **do not change this for GameCraft** unless you also retune the schedule.
8. **No image-to-video bootstrap weight set ≠ the reference-frame mode.** GameCraft does *not* ship a separate "I2V" checkpoint à la HunyuanVideo-I2V; the same single checkpoint handles both `single-reference-frame` (chunk 0, mask=1 on frame 0) and `single-historical-clip` (chunk N>0) modes purely by varying the channel-cat input. This is one of the contributions of the paper.

7. **Long-form quality cliff.** Paper claims "consistency across long temporal sequences" but doesn't publish a sharp number for when artefacts begin. Empirically, community reports suggest visible drift after 20+ chunks (≈26 s). Mitigation: re-anchor on the original reference image periodically.
8. **CFG-distillation residual.** Does the distilled checkpoint accept `--cfg-scale` >1 at all, or is it a no-op? Code review needed; likely a no-op (one forward per step regardless).
9. **VAE tiling support.** HunyuanVideo's diffusers VAE has `enable_tiling()`/`enable_slicing()`. The GameCraft repo wraps the same VAE — confirm the flags are preserved and that tiling is needed at 704×1216 for HartsyInference's target GPUs (RTX 3090 24 GB will require it).
10. **Quantisation tolerance.** Tencent ships an FP8 option (`--use-fp8`). For HartsyInference we'd target bf16 first and FP8/INT8 later. No public number for the quality delta of `--use-fp8` vs bf16 — need to benchmark.
11. **Plücker map dtype.** Paper / code likely use fp32 for Plücker computation then cast to bf16 before CameraNet. Confirm — small precision losses in ray geometry can show as visual drift over chunks.
12. **`Notice.txt` contents.** Acknowledges HunyuanVideo, SD3, FLUX, Llama, LLaVA, diffusers. Implementers must propagate this attribution into any HartsyInference NOTICE file for the Hunyuan-GameCraft package.

4. **Backbone implementation.** Parameterize `HunyuanVideoTransformer` over `(depth_double, depth_single, in_channels, has_camera, guidance_embed)` so the same class serves both vanilla HunyuanVideo (20/40, 16, false, true) and GameCraft (19/38, 33, true, false). Block code is identical.
5. **3D RoPE.** Implement `compute_3d_rope(rope_dim_list=[16,56,56], shape=(T_lat, H_lat//2, W_lat//2), theta=...)`. Theta per axis: HunyuanVideo uses `rope_theta=256.0` in diffusers — confirm against GameCraft source. Compute `freqs_cos` / `freqs_sin` once per chunk and cache.
6. **CameraNet.** ~200 LOC. Use existing `Conv2d` and `GroupNorm` from `HartsyInference.Core`. The PixelUnshuffle is a pure tensor reshape (no compute). The temporal pooling step is `(T, C, H, W) → (T', C, H, W)` with `T' = (T-1)/4 + 1` via causal stride-4 averaging of frames 1..T while keeping frame 0 — implement as a small custom op.
7. **Plücker generation.** Pure CPU code; runs once per chunk, ~1 ms at 704×1216×33. No backend kernel needed. Cache the unit ray directions in pixel coordinates at startup; per-chunk only the camera pose changes.
8. **Action → pose integration.** `ActionToPose` is a tiny state machine: `(action, speed)` → constant `(d_trans, d_rot, α, β)` for the chunk → integrate over 33 frames → 33 poses. Use double precision for the integration to avoid drift over long rollouts. Quaternion for rotation.
9. **VAE.** Reuse the future `HunyuanVideo3DCausalVae` decoder. Tiling required at 704×1216 on consumer GPUs (24 GB).
10. **Text encoders.** Llava-Llama-3-8B is just Llama-3-8B at the language tower — depend on `HartsyInference.Text.Llama` (or `dotLLM`) for the inference. Apply the diffusers prompt template + `crop_start=95` exactly. CLIP-L pooled is a tiny standalone encoder; we likely already have it for SD3/FLUX.
11. **CFG.** Two-pass CFG at scale 2.0 doubles the per-step transformer cost. At 30k tokens × 50 steps × 2 passes this is the dominant cost. Consider always-batched CFG (cat cond + uncond along batch axis) to halve the launch overhead — same trick FLUX uses.
12. **Distilled checkpoint.** Same code path; just swap the safetensors file, set `num_inference_steps=8`, skip the uncond pass entirely (`cfg-scale=1.0`).
13. **Streaming output.** The natural API is `async IAsyncEnumerable<VideoChunk>` yielding one 33-frame chunk at a time, with the caller supplying the next action via a callback or queue. Match `dotLLM`'s streaming token API where possible for consistency.
14. **Validation.** Reproduce the first frame of `asset/village.png + "w 0.2"` exactly (within bf16 tolerance) against the Python reference. Numeric tolerance budget: max-abs ≤ 1e-2 on the final decoded RGB frame after one chunk; mean-abs ≤ 1e-3. (Tight because flow-matching + CFG amplifies small precision errors over 50 steps.)
15. **Sample app.** `samples/HunyuanGameCraft.Interactive/` — a console app that takes `--reference-image`, `--prompt`, and reads action keys from stdin (`w/a/s/d`) to produce chunks on demand. Must display the license warning before doing anything.
16. **Documentation in `docs/Checklists/PHASE_10_INTERACTIVE.md`** must call out the license gate as a separate checklist item from "implement transformer" / "implement CameraNet" / "implement VAE decode."
17. **Do not** auto-resolve the model on `dotnet add package HartsyInference.Interactive.HunyuanGameCraft`. The first call into the package must explain how to acquire weights with full license context.
