## Summary

Hunyuan-GameCraft 1.0 (Tencent, paper arXiv 2506.17201, code + weights released 2025-08-14) is an **action-conditioned, image-and-text-prompted, autoregressive long-form video diffusion model** built for interactive game-style footage. The user supplies (a) a reference first frame, (b) a text prompt, (c) a sequence of discrete keyboard actions from the set `{w, a, s, d}` plus mouse signals each annotated with an action-speed scalar in `[0, 3]`. The model emits 33-frame, **720p (704×1216)**, 25 fps clips that can be chained autoregressively into arbitrarily long video by feeding prior frames as history conditioning.

The denoiser is a **drop-in re-instantiation of the HunyuanVideo MM-DiT transformer** (Tencent's 13B text-to-video model), retrained end-to-end on a corpus of >1 M gameplay recordings spanning 100+ AAA titles plus a fine-tuning pass on synthetic, precisely-annotated action–video pairs. Backbone config: `hidden_size=3072`, `num_heads=24` (`head_dim=128`), `depth_double_blocks=19`, `depth_single_blocks=38`, `mlp_ratio=4.0`, RMSNorm Q/K, 3D RoPE with `rope_dim_list=[16, 56, 56]` (t, h, w summing to 128 = head_dim), patch size `[1, 2, 2]`, latent in/out channels = 16. This puts the GameCraft transformer at the same ≈13 B-parameter scale as HunyuanVideo. (The author config `depth_double=19 / single=38` is one block fewer per stream than vanilla `HunyuanVideoTransformer3DModel` (20/40) — see § Differences.)

Two novel architectural pieces sit *on top of* that backbone:

- **CameraNet** — a lightweight 6-channel-in convolutional action encoder that turns the discrete `(w/a/s/d/mouse, speed)` sequence into a **Plücker-coordinate camera-ray map** (6 channels per pixel), spatially down-shuffles 8× via `PixelUnshuffle`, applies two `Conv2d → GroupNorm → ReLU` blocks with temporal pooling between them, projects to 16 channels, and patch-embeds into the same 3072-dim token space as the latent — then **adds** those tokens, scaled by a learnable per-channel coefficient initialized to zero, to the noisy latent tokens after patchify. Token-addition (not cross-attention) is the fusion mechanism.
- **Hybrid history conditioning** — every input latent gets a `+1` extra channel (`6` channels total post-cat instead of the 16-channel latent expectation, see § Channel layout for the actual concat ordering) that is a per-frame binary mask: `1` on frames that are history (the previous clip's clean latents, copied into the input), `0` on frames that are noisy / to-be-predicted. During training Tencent samples three regimes: 70 % single-historical-clip continuation, 5 % multiple historical clips, 25 % single reference-frame (first-frame image-to-video). At inference, autoregressive long-form rollout always uses the single-historical-clip path.

Text conditioning uses HunyuanVideo's dual encoder — **Llava-Llama-3-8B-v1.1** as the primary high-dim sequence encoder (≈4096-dim hidden, passed through a TokenRefiner) and **CLIP-ViT-Large-Patch14** as the pooled global encoder (768-dim). VAE is HunyuanVideo's **3D causal VAE** (`884-16c-hy0801`): 16 latent channels, 8× spatial compression, 4× temporal compression, causal-conv3d. Scheduler is **FlowMatchDiscreteScheduler** (`num_train_timesteps=1000`, `shift=5.0` at inference, `reverse=true`, Euler solver). CFG at scale 2.0 over 50 steps for the base model; a **Phased Consistency Model (PCM)** distilled variant runs in **8 steps with CFG=1.0** for ≈10-20× speedup, hitting 6.6 fps on the reference 8×H20 setup.

For HartsyInference: the **transformer code can be ≈98 % shared with a future HunyuanVideo pipeline** (only the input-channel count and the CameraNet attachment differ). The hard new work is (a) Plücker-ray generation from `(w/a/s/d, speed)` sequences, (b) the 3D causal VAE decoder, (c) Llava-Llama-3-8B text-encoder inference (likely shared with the native `HartsyInference.LLM` Llama backbone), and (d) a **`.pt` (PyTorch pickle) loader** — the weights ship only as `mp_rank_00_model_states.pt` (30.2 GB) and `mp_rank_00_model_states_distill.pt` (30.2 GB), not safetensors. See § File tree warning.

## Data Layouts / Formats

### Checkpoint format

- **Container**: PyTorch `.pt` (pickle) — *not* safetensors. ZIP archive containing `data.pkl` (a Python pickle stream calling `torch._utils._rebuild_tensor_v2`) plus `data/0`, `data/1`, ... blob files holding raw bf16 tensor bytes in little-endian. `OrderedDict` keys map tensor names → reconstituted tensors.
- **Layout**: flat state dict, **not** a nested `nn.Module` pickle. Loading is `state_dict = torch.load(path, map_location='cpu')`, then `model.load_state_dict(state_dict)`.
- **Model-parallel naming**: `mp_rank_00_` indicates DeepSpeed Megatron-style tensor-parallel rank 0. Current release ships only rank 0 (i.e. the model is materially single-GPU-shape; sequence parallelism is done dynamically at runtime via the `_sp` package). Future Tencent releases could in principle ship `mp_rank_01_...` etc.
- **Dtype**: bf16 throughout, including CameraNet.
- **Suggested key naming** (to verify by dumping with `torch.load` + `.keys()`):
    - `img_in.proj.weight`, `img_in.proj.bias` — patchify input projection (shape `[3072, 33, 1, 2, 2]` after factoring patch into channel — flatten gives 33*1*2*2 = 132 → likely `[3072, 132]` actual storage).
    - `txt_in.proj.weight`, `txt_in.proj.bias` — Llava-Llama → 3072 input projection.
    - `txt_in.individual_token_refiner.blocks.{0,1}.*` — TokenRefiner self-attn + FFN.
    - `time_in.mlp.{0,2}.{weight,bias}`, `vector_in.{...}` — timestep + CLIP-L embedding stacks.
    - `double_blocks.{0..18}.img_attn_qkv.{weight,bias}` / `.img_attn_proj.*` / `.img_mlp.{0,2}.*` / `.img_mod.lin.*` / `.img_norm1.*` / `.img_norm2.*` (similarly `.txt_*`).
    - `single_blocks.{0..37}.linear1.{weight,bias}`, `.linear2.{weight,bias}`, `.modulation.lin.*`, `.norm.*`, `.q_norm.scale`, `.k_norm.scale`.
    - `final_layer.linear.{weight,bias}`, `.adaLN_modulation.{1}.{weight,bias}`.
    - `camera_in.encode_first.{0,1}.{weight,bias}`, `camera_in.encode_second.{...}`, `camera_in.final_proj.{weight,bias}`, `camera_in.patch_embed.proj.{weight,bias}`, `camera_in.scale` — the learnable per-channel scale.

### Plücker camera-ray map

- Shape `(T=33, C=6, H=704, W=1216)`, fp32.
- Channels `[0..2]` = ray direction `d ∈ ℝ³`, normalized.
- Channels `[3..5]` = moment `m = origin × d ∈ ℝ³`.
- Origin: world-space camera position at frame `f` derived from cumulative `(d_trans, α)` integration.
- Camera intrinsics: pinhole; focal length implied by `(H, W) = (704, 1216)` and a fixed FOV (paper does not state the exact FOV — likely 60°; see Open Questions).

### Mask channel

- Shape `(B, T_lat=9, 1, H_lat=88, W_lat=152)`, fp32 in `{0.0, 1.0}` (not bf16, to avoid quantisation jitter in modulation downstream).
- `1` = history (clean reference latent), `0` = noise target.
- Broadcast vs per-pixel: in practice broadcast across `(H_lat, W_lat)` because a whole latent frame is either history-or-target.

### Latent input concatenation order

`x = cat([noisy_latent (B,9,16,88,152), ref_history_latent (B,9,16,88,152), mask (B,9,1,88,152)], dim=2)` → `(B, 9, 33, 88, 152)` → patchify to `(B, 9*44*76, 3072) = (B, 30096, 3072)`.

CameraNet output is added on top: `x_tokens += scale * cameranet(plucker_map)`.

## Differences Between Implementations

1. **Backbone block counts vs HunyuanVideo base.** GameCraft's `HYVideoDiffusionTransformer` defaults to `depth_double=19, depth_single=38`, while diffusers' `HunyuanVideoTransformer3DModel` defaults to `num_layers=20, num_single_layers=40`. Tencent likely trimmed one dual + two single blocks to spend the parameter budget on (a) CameraNet, (b) the wider 33-channel patchify input, (c) the extra training compute for hybrid history. **A diffusers-style loader will not load GameCraft weights without explicitly overriding these depths.**
2. **`in_channels` mismatch.** HunyuanVideo expects `in_channels=16`. GameCraft cats noisy + ref + mask = **33**. The patchify projection's first conv weight differs in shape. (Implementers must construct the backbone with `in_channels=33`, not 16.)
3. **`guidance_embed`.** Vanilla HunyuanVideo uses CFG-distilled embedded guidance (`guidance_embed=True`, accepting a `guidance` tensor as input). GameCraft uses **raw two-pass CFG** at base (`cfg-scale=2.0`) and one-pass at distilled (`cfg-scale=1.0`); the `guidance` argument is unused.
4. **Distilled variant is PCM, not Hyper-SD or LCM.** PCM (Phased Consistency Model) has different boundary-step training than the LCM family. At inference both run as straight `step` calls on a Euler-flow scheduler — no special PCM-specific sampler. So the HartsyInference scheduler code is identical between base and distilled; only `num_inference_steps` and `cfg-scale` change.
5. **CameraNet has zero-init final projection + zero-init scale.** Means a freshly-constructed CameraNet contributes nothing — useful for sanity-checking the rest of the pipeline before loading CameraNet weights. (Equivalently: if CameraNet weights fail to load, the model degrades to a text-only HunyuanVideo-like behaviour rather than producing garbage.)
6. **Single-stream-block modulation.** GameCraft's `SingleStreamBlock` uses **3-factor modulation** (`shift, scale, gate`) on a single concatenated stream, where the equivalent FLUX/HunyuanVideo block also uses 3-factor — confirm by tensor key. The double-stream block uses 6-factor per stream (12 total).
7. **`flow-shift-eval-video=5.0` is hardcoded for the 720p / 33-frame regime.** Lower shift values (e.g. 3.0) are used in HunyuanVideo for 540p; **do not change this for GameCraft** unless you also retune the schedule.
8. **No image-to-video bootstrap weight set ≠ the reference-frame mode.** GameCraft does *not* ship a separate "I2V" checkpoint à la HunyuanVideo-I2V; the same single checkpoint handles both `single-reference-frame` (chunk 0, mask=1 on frame 0) and `single-historical-clip` (chunk N>0) modes purely by varying the channel-cat input. This is one of the contributions of the paper.
