## 0. Abstract (≤ 200 words; written last)

Placeholder structure — fill in with measured numbers when B5 closes:

> Diffusion model inference on GPUs is dominated by Python frameworks (PyTorch, diffusers, ComfyUI) that deliver excellent performance but impose heavy runtime dependencies (Python interpreter, native CUDA wheels totalling > 5 GB, virtualenv complexity). Native C++ alternatives (e.g. stable-diffusion.cpp) trade dependencies for development cost. This work presents *SharpInference*, a managed-C# implementation that targets NVIDIA GPUs entirely through PTX kernels loaded via the CUDA Driver API — no native shared libraries beyond the system driver. We show that, with **N hand-written PTX kernels**, **kernel fusion at six block-level patterns**, **a tiled FlashAttention-2 implementation**, and **CUDA Graph capture of the per-step kernel sequence**, the C# backend reaches **R%** of PyTorch+diffusers throughput on **M models** across **K GPU generations** (Ampere, Ada, Hopper), with end-to-end SDXL 1024² generation in **T s/step** on a consumer RTX 3060 (vs **T_pt s/step** for PyTorch). We characterize the contribution of each optimization individually using **N=5 trial Welch's t-tests**, releasing all kernels, benchmarks, and result CSVs as open artifacts.

## 1. Introduction

### 1.1 Motivation

- Diffusion model inference is the dominant GPU workload for image / video / audio generation. Stable Diffusion / Flux / SD3.5 / Hunyuan / Z-Image / etc. use the same kernel patterns: GEMM-heavy DiT blocks, GroupNorm + SiLU stacks, scaled-dot-product attention, Conv2D 3×3.
- Industry-standard runtime is PyTorch + diffusers (used by ComfyUI, InvokeAI, Automatic1111, etc.). Performance is excellent but the deployment story is heavy: 5+ GB of native wheels, Python interpreter, virtualenv management. For embedded inference (desktop apps, games, server backends written in non-Python languages) this is a non-starter.
- Lightweight alternatives exist (`stable-diffusion.cpp` is the canonical example) but require shipping additional native binaries per platform and target a single ecosystem.
- **Gap**: no published evidence of how close a managed-language inference engine — *one binary, no native deps beyond the driver* — can come to PyTorch performance. Existing comparisons (e.g. ML.NET, ONNX Runtime CSharp) wrap native runtimes.

### 1.2 Contribution

1. **A measurement-driven optimization framework** for diffusion inference that produces statistically rigorous before/after data per kernel and per model, across multiple GPU generations.
2. **An open-source PTX kernel library** for diffusion-relevant ops (GEMM, Conv2D, GroupNorm, LayerNorm, RmsNorm, SDPA-FA2, SiLU/GeLU/GeGLU, BroadcastAdd) callable from managed C# via the CUDA Driver API.
3. **An empirical characterization of where the gap closes**: per-optimization speedup contribution, statistical significance, accuracy preservation.
4. **A negative result**: where a hypothesized optimization (e.g. memory pooling, when the baseline already uses `cuMemAllocAsync`) provides < 1.1× speedup, we report and discuss.
5. **Reproducibility artifact**: `bash benchmarks/run_benchmarks.sh` on any CUDA box reproduces our numbers within noise.

### 1.3 Non-Goals

- Multi-GPU scaling (the SharpInference workloads are single-GPU latency-bound).
- Training or fine-tuning (inference only).
- Beating CUDA C++ — we target *parity with optimized PyTorch + cuDNN + cuBLAS*, which itself sits on top of CUDA C++.
- New attention algorithms — we implement FA2 as published, not a novel algorithm.
- CPU performance — covered separately.

## 2. Background

### 2.1 GPU Memory Hierarchy and Kernel Launch Overhead

- HBM vs L2 vs SRAM bandwidth; figure copied from FlashAttention paper, attributed.
- Per-kernel launch CPU overhead (~5–10 µs); 4 000+ launches/step at 1024² SDXL → 20–40 ms/step just on launches.

### 2.2 Diffusion Model Architecture (Brief)

- UNet (SDXL) vs DiT (Flux, SD3.5, etc.).
- Common kernel patterns: GroupNorm+SiLU, Linear+bias+activation, AdaLN-Zero (RmsNorm + (1+scale)·· multiply).
- Self-attention shapes (table reproduced from FLASH_ATTENTION.md).

### 2.3 PTX vs CUDA C vs Triton

- PTX is NVIDIA's assembly-like portable kernel format. Loaded at runtime via `cuModuleLoadData`. JIT-compiled per-device.
- CUDA C compiles via `nvcc` to PTX; we author CUDA C and ship the compiled PTX.
- Triton is an alternative; not used here because Triton requires a Python toolchain at compile time. (We can author with `nvcc -ptx` and ship pure binaries.)

### 2.4 Why Not Just Wrap libtorch

- libtorch is 4 GB. SharpInference's PTX kernels are ~200 KB total.
- libtorch's API is C++; managed-language bindings introduce marshalling per call.
- Pinning the libtorch version locks deployments to a specific CUDA toolkit; our PTX kernels are JIT'd per device.

## 3. The SharpInference Architecture

### 3.1 Layered Backend Design

- `IBackend` interface; CPU + CUDA + Vulkan implementations.
- `Tensor` abstraction with lazy GPU sync; figure: lazy-sync state machine.
- Weight cache + activation cache.

### 3.2 Op Dispatch via Driver API

- One `cuModuleLoadData` per PTX file at backend construction.
- One `cuLaunchKernel` per kernel call. No CUDA Runtime API.
- cuBLAS used via P/Invoke for GEMM; cuBLASLt for FP8 GEMM (Ada+).

## 5. Optimizations

Each subsection: motivation, design, implementation summary, results figure, statistical test outcome.

### 5.1 FlashAttention 2 Tiled SDPA

- Why: vanilla SDPA materializes O(Sq · Skv · heads · dtype-bytes); at SDXL 64×64 self-attn that's 6 GB just for the scores buffer.
- Algorithm reference: Dao 2023 (FA2); spec details in `FLASH_ATTENTION.md`.
- Implementation in PTX: tiles, online softmax, wmma Tensor Cores.
- Results table: per-shape latency vs PyTorch SDPA, t-test outcome.
- Per-model end-to-end speedup contribution (isolated via A/B with FA enabled/disabled).

### 5.2 cuDNN Conv2D Winograd

- Why: 3×3 stride-1 dominates UNet/VAE; Winograd has fewer multiplications than direct convolution.
- Cudnn algorithm-selection heuristic.
- Workspace management in C#.
- Results: Conv2D microbench, SDXL UNet step time.

### 5.3 Kernel Fusion Patterns

- LinearBiasSilu, LinearBiasGelu, RmsNormModulate.
- HBM-traffic reduction calculation (per input tensor visited once instead of N times).
- Results: per-block latency (NVTX-measured), launch count reduction.

### 5.4 Memory Pool

- Free-list per size class; bucket-allocated fast path.
- Why this is potentially a *negative result* on systems already using `cuMemAllocAsync`.
- Results: alloc/free microbench, per-step time variance reduction.

### 5.5 CUDA Graphs

- Capture-once-replay-many for the denoise step.
- Device-side scalar passing for timestep / sigma.
- Re-capture trigger on shape change.
- Results: launch overhead before/after, per-step time.

### 5.6 F16 / BF16 / FP8 Audit

- Promotion table: which ops promoted to F32 unnecessarily, which had to stay.
- Tensor Core utilization measurements via Nsight Compute.
- Cross-device matrix: Ampere / Ada / Hopper.

## 7. Discussion

### 7.1 Where the Remaining Gap Lives

- Driver overhead floor (per-launch 1–5 µs even with CUDA Graphs)
- cuBLAS / cuDNN versions PyTorch uses are sometimes ahead of stable releases (fast-track autotune)
- Tensor Core utilization ceiling on consumer cards (smaller register files than datacenter cards)

### 7.2 Engineering Lessons

- Measure first, optimize second
- Statistical rigor matters: we caught two "obvious" wins that didn't survive a t-test
- The C# tooling (BenchmarkDotNet, dotnet test) is sufficient for this work; no Python required for the benchmark side

### 7.3 Generalization

- Does this transfer to non-diffusion workloads? (LLM inference, vision models — not measured here, but the kernels port.)
- AMD ROCm — out of scope; HIP can transpile some PTX but our cuBLAS/cuDNN dependencies wouldn't transfer.

### 7.4 Threats to Validity

- One vendor (NVIDIA only)
- One framework comparison (PyTorch + diffusers); not vs TensorRT or ONNX Runtime. (Possible follow-up work.)
- Inference only; training shapes / patterns differ
- Our numbers are upper-bounds: a determined optimizer with more time per kernel could close the remaining gap further

## Drafting Discipline

- **Never write claims without a citation to `benchmarks/results/`**. If a number isn't in a CSV, it doesn't go in the paper.
- **Negative results are first-class**. If FA2 doesn't beat naive SDPA at small shapes (e.g. cross-attn with 77 KV tokens), that goes in § 5.1 explicitly.
- **Keep figures regenerable**. Every figure has a `benchmarks/figures/<figure>.py` that reads from CSV → matplotlib → PDF.
- **Keep the writing measured**. "Our implementation achieves X% of PyTorch performance" not "our implementation is faster than PyTorch". The point is the methodology + the kernel library, not the numbers in isolation.
