## Pipeline

```
mesh -> P3-SAM (point-prompted 3D segmentation, 400 FPS prompts, NMS, face labels, AABBs)
     -> X-Part (conditioned flow-matching DiT: one latent per part, decoded by a shape VAE)
```

## P3-SAM (`P3-SAM/model.py`, `P3-SAM/demo/auto_mask.py`)

- Weights: `p3sam/p3sam.safetensors` 450,968,044 B, sha256 `eb76550cfbe06f154c6e9b17167ccfc28222bb4a216ec7b12ac2bf7d762de38c`, plus `p3sam/config.json` (134 B). Header read 2026-11-11 (ranged read of the first 53,448 bytes, JSON only, the file was not saved): 513 F32 tensors, no metadata. The Sonata backbone is inside: `sonata.embedding` (5 tensors) and `sonata.enc` (448 tensors, 108.46 M parameters), so `facebook/sonata` is not needed. The heads are `mlp` (1.16 M), `seg_mlp_1..3` (0.53 M each), `seg_s2_mlp_g` and `seg_s2_mlp_1..3` (0.27 M each), `iou_mlp` (0.33 M) and `iou_mlp_out` (0.13 M), each 6 tensors (three Linear weights and biases), which matches the module definitions in `model.py`. The full key list is in the session scratchpad, not in the repository.
- Feature extractor: Sonata (PTv3 encoder, `in_channels` 9 = coord, color (ones), normal; stages 48/96/192/384/512 with depths 3/3/3/12/3, heads 3/6/12/24/32, patch 1024, serialisation orders z, z-trans, hilbert, hilbert-trans with shuffling, stride 2 pooling, `enc_mode`). `get_feat`: sample 100,000 surface points, normalise to the unit cube, run Sonata, unpool by concatenating each parent's features with its children's (`pooling_parent`/`pooling_inverse`) down to the finest level, giving 1232 channels, then an MLP 1232 -> 512 -> 512 -> 512, then gather per point.
- Heads (plain MLPs, GELU): stage 1, three mask heads over `[feat 512, point xyz, prompt xyz]` (518 -> 512 -> 512 -> 1); stage 2, a global MLP over `[.., stage-1 logits]` (521 -> 256 x3), max over points, concatenated back, then three mask heads (777 -> 256 -> 256 -> 1); an IoU head (max-pooled, 256 -> 3). `iter=1` stage-2 passes. Outputs: three masks per prompt (sigmoid > 0.5) and three predicted IoUs.
- Auto mask (`mesh_sam`): clean the mesh, build face adjacency, sample 100k points and their face normals, 400 farthest-point-sampling prompts (`fpsample`), prompts in batches of 32, sort by predicted IoU, mask NMS by IoU, assign faces from points, fix labels by connected regions over face adjacency (with AABB checks), optional post-process (merge parts whose integral area exceeds 0.95 and that are under 1 % of the area), then per-part AABBs.
- Not portable as is: `fpsample` (FPS, a small C++ extension; the toolkit equivalent is `SurfaceSampler.FarthestPointIndices`), trimesh sampling and face adjacency, numba adjacency, `utils/chamfer3D` (CUDA, only in demos). All of it is plain geometry that the toolkit can host (the toolkit already has surface sampling, BVH, adjacency).

## X-Part (`XPart/partgen`, `config/infer.yaml`)

- Weights: `model/model.safetensors` 6,630,571,584 B (the DiT; BF16, see the 2026-11-12 section below), `shapevae/shapevae.safetensors` 655,539,474 B, `conditioner/conditioner.safetensors` 1,755,920,004 B, `p3sam/p3sam.safetensors` above; configs `model/config.json`, `shapevae/config.json`, `conditioner/config.json`, `scheduler/config.json`. The release is "a light version of X-Part" (README); the full model is only on Hunyuan3D-Studio. Recommended inputs: scanned or AI-generated meshes.
- DiT (`PartFormerDITPlain`): width 2048, depth 21, 16 heads, RMS q/k norm, no biases, learned part embedding (`valid_num` 50), two cross-attentions (object tokens and part-in-bbox tokens, both 1024-wide), MoE in 6 layers (8 experts, top-2), 1024 latent tokens of 64 channels. This is the same family as the Hunyuan3D-2.1 shape DiT, which this repository already runs (MoE routing included). Structure checked in `partformer_dit.py` and `moe_layers.py`: the MoE block has a shared expert (as in 2.1); U-skips (`skip_linear` over a concatenation, then a norm) on layers 11 to 20 (`layer > depth // 2`); the time embedding is prepended as one token (`torch.cat([c, x])`). Not yet compared: the head-split order inside `Hunyuan3DPlainBlock.Regroup` (the q/k/v are separate tensors as in 2.1, so only the head layout is open). A parity trap: with `use_part_embed` the forward adds `part_embed[torch.randperm(valid_num)[:num_parts]]` (random part ids at inference), so a reference run needs the permutation pinned.
- Scheduler: `FlowMatchEulerDiscreteScheduler`, 1000 training steps, flow matching with an Euler integrator (the repository already has the Hunyuan3D flow sampler).
- Shape VAE (`VolumeDecoderShapeVAE`): 1024 latents x 64, width 1024, 8 encoder and 16 decoder layers, 8 Fourier frequencies, `qk_norm`, 81,920 surface points, scale factor 1.0039506. Hunyuan3D shape VAE family, with a different latent count; the conditioner uses two copies (4096 latents each (the object, and the part in its box)).
- Conditioner: ShapeVAE object and local encoders plus a Sonata feature extractor (`use_seg_feat`), the P3-SAM output giving the part boxes.

## Implemented (2026-11-12, branch `feat/hunyuan-part-p3sam`)

`ThreeD/Models/Hunyuan3D/Part`: `P3SamCheckpoint` (the `sonata.` tensors to the Utonia encoder, the rest to the heads), `P3SamGridSample` (Sonata's `CenterShift` and `GridSample` at 0.005 with the FNV hash), `P3SamFeatures` (encoder, stage gathering through the pooling maps, the 1232 to 512 MLP, per-point expansion), `P3SamHeads` and `P3SamMlp` (the mask and IoU MLPs, with the prompt-independent first-layer terms computed once per mesh and held as backend tensors; a prompt runs on the backend with F32 GEMMs and only the per-point logits and the two max-pool inputs return to the host, so no prompt batch is needed: the work buffers are three `[points, 512]` tensors, about 2.3 GB on the device with the eight first-layer terms at 100k points; the max-pool reads two `[points, 512]` tensors back per prompt until a device row-max exists; `Own` sets `ForceF32Gemm`, so the 1232 to 512 feature MLP also runs F32 GEMMs), `P3SamPartLabeler` (the step-for-step port of the auto-mask heuristics), `P3SamAutoMask` (surface sampling, 400 farthest-point prompts, best-IoU mask per prompt, per-stage log). `UtoniaConfig.Sonata` and the `UseRope` switch make the existing Utonia encoder the Sonata backbone (same tensor names, no `attn.rope.inv_freq`).

Tested on random weights first (superseded by the real-weight comparison below): the heads against a transcription of upstream's concatenate-then-MLP (4 decimals; it shares this repository's reading of the column order, which the real-weight comparison proves), the grid sample, the feature gather, the labeler on synthetic cubes, and a tiny whole run. Not done: engine and CLI wiring, GPU runs. Differences from upstream: the encoder uses the fixed order sequence, while upstream permutes the serialisation orders at random on every pooling (see the real-weight section), the surface sampler is this repository's generator (the Python seed does not reproduce its points), `fpsample` is replaced by `SurfaceSampler.FarthestPointIndices` (the prompts can differ), the voxel pick is random as in upstream's train-mode `GridSample` (a deterministic mode exists), and the mesh cleaning (`merge_vertices`, `process`) is left to the caller.

## Engine and CLI (2026-11-12)

`P3SamPipeline` (`ThreeD/Pipelines`) loads `p3sam.safetensors` and runs `P3SamAutoMask` on the mesh after the upstream cleanup (`MeshCleaner`: weld, degenerate and duplicate faces, unreferenced vertices), so the result's faces refer to the cleaned mesh. `PartGlbWriter` writes one node, mesh and flat-coloured material per part (`part_{id}`, golden-angle hues), faces with no part in a grey `unassigned` node; each node's `extras` hold `partId`, `faceCount` and `aabb`. `MeshService` takes id `hunyuan3d-part` (`MeshModelIds.PartMesh`): `MeshRequest.SceneMesh` in, `Seed` fixes the surface sampling, no image, steps or grid; the catalog entry downloads the one 451 MB file into `3D/hunyuan3d-part/p3sam/` (sha256 pinned). `hartsy 3d part.glb -m hunyuan3d-part` writes the GLB and prints `part N: faces, box`. Point and prompt counts are upstream's (100,000 and 400). For parity-grade features use `--profile reference` (or `numerics.sdpaNoTf32`), see the GPU section.

What differs from the 2.1 DiT the engine already runs (`Hunyuan3DPlainDit`, `Hunyuan3DPlainBlock`): a second cross-attention with its own norm per block (the 2.1 `model.*` group has 752 tensors; `attn2_2` plus `norm2_2` add 9 x 21 = 189 and `part_embed` 1, which gives the 942), the learned part embedding (random part ids at inference upstream, see the parity trap above), the bounding-box token allocation (`allocate_tokens`), and BF16 weights (the 2.1 file is F16; BF16 widens exactly to F32). The conditioner holds F32 Sonata weights beside BF16 VAE weights.

Run shape upstream (`partformer_pipeline.py`): the mesh is normalised to a 0.8 box, P3-SAM's auto-mask boxes give K parts, 81,920 surface points of the object and of each part inside its box feed the two conditioners, the DiT denoises K latents of 1024 x 64 as a batch (one latent set per part; `guidance_scale` -1, the default, means no classifier-free guidance) over 50 flow-matching Euler steps (`num_inference_steps` 50; `sigmas = np.linspace(0, 1, 50)` ascending, the scheduler appends a terminal 1, the DiT gets `t / 1000` where `t = sigma * 1000` (the scheduler's `timesteps = sigmas * num_train_timesteps`), so the sigma itself, which `partformer_dit.py`'s `TimestepEmbedder` embeds directly with `Timesteps(hidden_size)`, `scale` 1 and no `time_factor`: the same as the 2.1 plain DiT (`Hunyuan3DPlainDit` embeds the sigma as given, and `Hunyuan3DFlowSchedule.DitTimestep` returns it), so that code is reused unchanged; only the 2.0 Flux-style `Hunyuan3DDit` applies a `time_factor`; the update is `prev = sample + (sigma_next - sigma) * model_output`, the same convention as `Hunyuan3DScheduler`, where t = 0 is noise), each part latent is decoded and extracted at octree resolution 512, and the parts are mapped back to the input frame.

### Port plan (one PR each, CPU oracle first)

1. ShapeVAE encoder only (`input_proj`, cross-attention, 8 self-attention blocks, `ln_post`; no KL head, which X-Part never runs on the encoder side) from the X-Part file; compare against `partgen/models/autoencoders`. Start from `Models/UniRig/UniRigShapeEncoder.cs`, which implements the same `input_proj` / `cross_attn` / `self_attn.resblocks` key family (check how far it generalises); the decoder is `Hunyuan3DShapeVae` unchanged.
2. `PartFormerDITPlain`: the second cross-attention, part embedding, token allocation; oracle on random inputs with the part ids pinned (upstream draws them with `torch.randperm`).
3. Conditioner: object and local encoders, Sonata features (`sonata_extractor.py`; the code of the P3-SAM Sonata with its RoPE off can be reused, but not its weights: the conditioner's 453 Sonata tensors differ from P3-SAM's in all 453 (sha256 over the raw stored bytes of each tensor, both files F32 with equal shapes; the tensor bytes were read for this comparison only, nothing was inspected numerically), so two Sonata instances are loaded, about 430 MB each in F32; compute the Sonata features first and free both backbones before the 6.6 GB DiT is loaded), the 1232 to 512 MLP.

## X-Part pipeline (2026-11-12)

`XPartPipeline` (`ThreeD/Pipelines`) strings the verified pieces together, following `partformer_pipeline.py`: the mesh is normalised (`XPartSampling.Normalize`: centre to the origin, longest side 1.6); P3-SAM (`P3SamPipeline`) gives the part boxes on the normalised mesh; the object is sampled at 81,920 area-weighted surface points with face normals, and for each box the faces with a vertex inside it are sampled the same way (`sample_bbox_points_from_trimesh`; the sharp-edge label is 0 because the release samples no sharp edges); 4,096 farthest-point queries per encoder (upstream starts at a random point; the seed picks it here); `XPartConditioner` makes the object and part tokens; `XPartDit` denoises one 1024 x 64 latent set per part together over 50 Euler steps of the flow (`sigma` 0 to 1, `Hunyuan3DFlowSchedule`, no classifier-free guidance, `torch.randperm` part ids replaced by a seeded selection); each latent is scaled by 1 / 1.0039506, decoded by `Hunyuan3DShapeVae` on a grid and meshed at logit -1/512 (upstream `mc_level`), then mapped back to the input frame; the parts leave as meshes and as one GLB with a coloured node per part. Each stage loads its checkpoint and releases it, so the peak is the DiT. The DiT loads with `halfWeights`: the BF16 matrices become F16 (6.6 GB, not 13 GB as F32), the same path the 2.1 DiT uses.

Differences from upstream, all inputs of the run: a dense grid (default 256 per axis) instead of the octree at 512; no `fix_mesh` post-processing of the parts; the random draws (surface points, farthest-point starts, part ids, noise) differ from torch's, so a run is not comparable sample by sample, only part by part against the verified stages. Unit tests cover the geometry (`XPartSamplingTests`) and the half-weight path; the first end-to-end run is below.

**First real run (RTX 3060, 12 GB; the TRELLIS.2 bust welded and decimated to 40,080 faces; grid 256, 50 steps, seed 42, one process, `xpartrun` scratch runner, wall 385 s of an 8 min budget).** P3-SAM found 3 parts (head and hair, jacket and base, moustache). Stage times from the progress log: P3-SAM and its load 66 s; conditioning (Sonata features, both encoders at 81,920 points, 3 parts) 21 s; DiT load into F16 about 20 s and then 2.4 s per step, 50 steps to 236 s; VAE decode and marching cubes of the 3 parts 141 s (about 47 s per part at 256^3, the slowest stage per output: a candidate for the FlashVDM-style decoder); peak VRAM 9.53 GB (baseline 1.31 GB, delta 8.2 GB, so the 6.6 GB F16 DiT fits with its activations). Results: 3 meshes of 109,456, 152,036 and 7,644 faces, all watertight, whose bounds match the P3-SAM boxes. Judged by eye from a flat-colour render (`xpart_bust_parts.png` in the session notes): each part is a complete, clean shape that continues the others (the head and hair with the face, the jacket with the base, the moustache as its own piece), with the surface detail of the input; no floaters. Not compared with the Python pipeline end to end (no GPU Python reference); one object, one seed.

### Engine and CLI (X-Part)

`MeshModelIds.XPartMesh` (`hunyuan3d-xpart`, in `All`); the catalog entry `hunyuan3d-xpart` carries the four files of `tencent/Hunyuan3D-Part` under `3D/hunyuan3d-part` with their sha256 (the P3-SAM file is the same one `hunyuan3d-part` downloads, so one copy serves both): `p3sam/p3sam.safetensors` 451 MB, `conditioner/conditioner.safetensors` 1.76 GB, `shapevae/shapevae.safetensors` 656 MB, `model/model.safetensors` 6.63 GB (9.04 GB together). `MeshService.GenerateXPartAsync`: `MeshRequest.SceneMesh` in (obj or glb), `Seed` (negative: 42), `Steps` (0: 50, at most 1000), `GridResolution` (0: 256, 32 to 512); `Image`, `ScenePrompt` and a seed above `int.MaxValue` are rejected; the folder is the one holding the four files (or one level up from a file or subfolder of it, `MeshService.XPartFolder`, which names the missing files). The result is a GLB with one coloured node per part and `MeshResult.Parts` (id, box, face count). CLI: `hartsy 3d bust.glb -m hunyuan3d-xpart --steps 50 --grid 256`, which prints the parts.

### Flow loop against upstream (2026-11-12)

The Euler loop is `XPartPipeline.Integrate`; `XPartFlowParityTests` compares it with upstream's own `FlowMatchEulerDiscreteScheduler` and the denoising loop of `XPartPipeline.__call__` (oracle `tests/python-reference/dump_xpart_flow.py`) with the same noise and a toy velocity in place of the DiT: 50 steps and 7 steps agree to relative L2 8.2e-9 and 5.4e-9, with identical sigmas and timesteps within 6e-8. Read against the source, not run: the part-in-box face rule and the mesh normalisation. A whole-pipeline comparison is not possible: upstream's samples come from `trimesh.sample.sample_surface` and numpy's generator, so this repository's seeded sampler draws other points, and one 3-part forward on the C# CPU backend takes over half an hour.

### FlashVDM decode (2026-11-12)

`XPartOptions.FastDecode` (off by default) decodes each part with `Hunyuan3DShapeVae.DecodeFlashVdm` (the hierarchical decoder of the 2.1 turbo builds: a coarse grid, then only a band around the surface at each finer level, with adaptive key selection; the same VAE weights) instead of the dense grid. Upstream's X-Part decodes densely, so this approximates the dense field. Same bust, seed and settings as the first real run, grid 512 (RTX 3060, one process, wall 445 s of an 8 min budget, peak VRAM 9.57 GB): decode of the 3 parts 113 s in total (60, 33 and 20 s; the first includes warm-up) at 512, against 141 s (47 s each) for the dense grid at 256 and an estimated 6 minutes per part for a dense 512 (8 times the cells). Part meshes 425,784 / 595,396 / 26,261 faces (the dense 256 ones had 109,456 / 152,036 / 7,644). Agreement with the dense meshes (Chamfer distance over 40,000 surface samples each, so it includes the grid difference): mean 0.44 %, 0.41 % and 0.69 % of the part's extent, 99th percentile 1.0 %, 1.0 % and 8.5 % (the moustache), volumes within 0.2 % (0.0421 / 0.0583 / 0.0001 against 0.0420 / 0.0582 / 0.0001). The first two parts stay watertight; the moustache has small openings. By eye (`xpart_bust_parts_flashvdm512.png` in the session notes) the surface is smoother and sharper than the dense 256 (hair strands, jacket folds), with a few small rectangular notches on the back of the jacket that look like block boundaries of the hierarchy. Not compared with a dense 512 of the same latents (too slow), nor against upstream's octree extraction.

**Engine and CLI.** The option is the runtime setting `numerics.xpartFastDecode` (off by default; `hartsy 3d <mesh> -m hunyuan3d-xpart --set numerics.xpartFastDecode=true`), read for each request by `MeshService` and described in the model's profile note. `MeshService.XPartOptionsFor` maps the request and the setting to `XPartOptions` (unit-tested); the CLI path itself has not been run on the GPU with it. The asset status (`MeshAssetService`) follows what the loaders read when a path is given: P3-SAM takes the checkpoint file or the folder holding it, X-Part the install folder or a file or subfolder in it, reported file by file.

Caveats found in review: "grid 512" is 504 cells at the finest level (the levels are 63, 126, 252, 504, so 505^3 points, against 257^3 for the dense 256), not 513^3. The adaptive key selection takes `topK = latents / 3` = 341 of the 1024 latents (`Hunyuan3DShapeVae.DecodeFlashVdm` only defines 3072 and 512 latents; upstream never defined a value for X-Part's 1024), which may account for part of the moustache tail (99th percentile 8.5 %) and the rectangular notches; a larger `topK` or no selection (full attention over 1024 keys is cheap) is untested. The moustache is thin and small, so a band that is too narrow at the coarse 63-cell level would also fit its small openings; if the option ever became the default, a part with a small box should be decoded densely or checked for watertightness.
