# H0 — per-workload `ncu` top-5 kernel tables (RTX 3060)

**Item:** INFERENCE_ACCEL_GRIND.md §H0, the open "capture top-5 kernels per model" sub-item under the
ncu-access-check bullet. Method: `ncu --metrics <explicit list> --csv --target-processes all` (not
`--set basic`/`--set full` — an explicit metric list is deterministic, fast, and guarantees the three
roofline columns the checklist names resolve on every kernel), CSV parsed and aggregated per kernel name
(sum `gpu__time_duration.sum` across all launches of that kernel; % of sampled GPU time = that sum over
the grand total across all captured kernels). GPU: RTX 3060 only (`CUDA_VISIBLE_DEVICES=1`, this box's
reversed CUDA-vs-nvidia-smi ordering — nvidia-smi index 0). `ncu` runs as root via the scoped
`sudo -n <ncu-path>` NOPASSWD entry (only the profiler process itself is elevated; CSV output is
redirected by the invoking unprivileged shell via `>`, so the result files land already user-owned —
no `chown` needed on this run, unlike the checklist's original `-o <report>` recipe where ncu itself
writes the file as root).

Metrics captured (all four map straight to the checklist's roofline table):
`gpu__time_duration.sum` (kernel wall time, for ranking), `dram__throughput.avg.pct_of_peak_sustained_elapsed`
(DRAM bandwidth roofline %), `sm__throughput.avg.pct_of_peak_sustained_elapsed` (SM/compute roofline %),
`sm__pipe_tensor_cycles_active.avg.pct_of_peak_sustained_elapsed` (tensor-core pipe utilization %),
`sm__warps_active.avg.pct_of_peak_sustained_active` (achieved occupancy %).

## GPU hygiene note

First capture attempt was invalidated: `nvidia-smi` was checked, then the profiling command was queued in
the same tool call before confirming the check applied to the moment of launch — a concurrent session was
mid-run on the 3060 (`TextDecodeThroughputBenchmark`, PID 3403101, 93-96% util, ~6-8 GB) at the exact
moment the capture fired. That capture was discarded unread (rm'd, never aggregated into the tables

## Workload 1: `StepCacheKernelTests` (device-resident feature-cache reduction, §H1.3 gate)

Command:
```
sudo -n $NCU --metrics gpu__time_duration.sum,dram__throughput.avg.pct_of_peak_sustained_elapsed,\
sm__throughput.avg.pct_of_peak_sustained_elapsed,sm__pipe_tensor_cycles_active.avg.pct_of_peak_sustained_elapsed,\
sm__warps_active.avg.pct_of_peak_sustained_active --csv --target-processes all -- \
  env LD_LIBRARY_PATH=$HOME/.local/lib/cuda13 CUDA_VISIBLE_DEVICES=1 \
  dotnet test tests/HartsyInference.Cuda.Tests/HartsyInference.Cuda.Tests.csproj -c Release --no-build \
  --filter "FullyQualifiedName~StepCacheKernelTests"
```

No `--launch-count`/`--launch-skip`: this suite launches only a handful of kernels total (4 tests, each
one `RelativeL1Distance` call → 1-2 kernels), so the whole short run was captured, not sampled.

This suite exercises **only 2 distinct kernels** across 3 launches total — reported both, not a top-5
(there is no 3rd–5th to show). "Avg duration" = mean over all launches of that kernel; the metric columns
(occupancy/DRAM/SM/tensor) are from the single largest-shape launch (the 4096×1536 F32 case, 158 µs) —
the only real variation here is F32 (large shape) vs F16 (large shape); the 512×768 identical-tensors
launch is a 3rd, smaller F32 launch folded into the same kernel's average.

| Kernel | % of sampled GPU time | Avg duration | Achieved occupancy | DRAM throughput % | Roofline read |
|---|---|---|---|---|---|
| `stepcache_rel_l1_f32` | 66.4% | 85.9 µs | 96.9% | 92.9% | **Memory-bound** — DRAM at 92.9% of peak, SM only 12.2%, occupancy already near-saturated (96.9%). Command:
```
sudo -n $NCU --metrics gpu__time_duration.sum,dram__throughput.avg.pct_of_peak_sustained_elapsed,\
sm__throughput.avg.pct_of_peak_sustained_elapsed,sm__pipe_tensor_cycles_active.avg.pct_of_peak_sustained_elapsed,\
sm__warps_active.avg.pct_of_peak_sustained_active --csv --target-processes all -- \
  env LD_LIBRARY_PATH=$HOME/.local/lib/cuda13 CUDA_VISIBLE_DEVICES=1 \
  dotnet test tests/HartsyInference.Cuda.Tests/HartsyInference.Cuda.Tests.csproj -c Release --no-build \
  --filter "FullyQualifiedName~SageSdpaMicroBench"
```

This suite runs `[1,24,{2048,3072,4096,4608,6144,8192,12288},128]` across two theory methods (the
F32-vs-cuDNN-F16 crossover and the F16-ingest-vs-native-cuDNN-F16 crossover), so each kernel launches
many times at different Skv. Ranking (% of sampled time) sums `gpu__time_duration.sum` over **every**
launch of a kernel; the metric columns (occupancy/DRAM/SM/tensor) are read from that kernel's **single
largest-shape launch** (Skv=12288, the video-DiT-class shape — grid `(192,24,1)` for the two Sage flash
kernels) rather than averaged blindly across a 2048-seq call and a 12288-seq call, per the checklist's
own house methodology (steady-state / heaviest-shape read, not a cross-shape blend). 516 launches, 11
distinct kernels captured; grand total sampled GPU time 2.828 s.

|---|---|---|---|---|---|---|

per-row/per-channel reduction kernels; not worth further optimization at this time share.

## Roofline read key

- **Memory-bound**: DRAM% high (≳70%), SM/tensor% low → kernel is data-movement limited; the fix is
  fewer bytes moved (fusion, better dtype, tiling) not more compute.
- **Compute-bound**: SM% or tensor-pipe% high (≳70%), DRAM% low → kernel is arithmetic/issue limited;
  the fix is better instruction mix or higher-throughput ops (e.g. tensor-core vs scalar).
- **Latency-bound**: both DRAM% and SM/tensor% low, occupancy also low → kernel is stalled on
  dependencies/serialization, not saturating either roofline; the fix is more parallelism (occupancy,
  ILP) or removing sync points, not raw bandwidth/FLOP work.

## Most actionable finding

**The Sage INT8 flash kernel's occupancy ceiling (~25%, register-capped) — not either roofline — is the
single biggest lever in this capture.** `sage_attn_int8_v1_d128_f32` + `sage_attn_int8_v1_d128_f16io`
together are **85.8% of all sampled GPU time** across the SageSdpaMicroBench workload, and both sit at
the *identical* ~24.9% achieved occupancy while neither DRAM (3–5%) nor tensor-pipe (37.7–46.6%) is
anywhere near saturated. That's the textbook signature of a latency/occupancy-bound kernel: the SM has
work and bandwidth to spare, it just doesn't have enough resident warps to hide instruction/dependency
latency, because the kernel's register footprint (168 regs/thread per the H4 build log) caps it at 3
blocks/SM out of a higher theoretical ceiling. This corroborates — with fresh, independently-captured
numbers — the build log's own diagnosis (`docs/Checklists/INFERENCE_ACCEL_GRIND.md` §H4: "69.3% of
stalls are short-scoreboard on SMEM fragment loads... occupancy 24.25%").

Practical read: since this one kernel pair dominates the workload's time budget, **register-pressure
reduction that raises occupancy toward the theoretical ceiling (without spilling — the `+bounds(3)`
attempt in the same log already showed that a naive register cap induces spills that eat the gain) is
worth more than any further work on the already-fast, already-memory-saturated V-transpose prologue
(`sage_v_f16t`/`sage_v_f16t_h`, 9.2% combined, already 60–65% DRAM and >97% occupancy) or the sub-1%
quant prologues.** The stepcache kernels are a closed case (93%/86% DRAM, correctly shipped as-is); the
cuDNN incumbent itself profiles even worse (16.7% occupancy) at these shapes, which is the whole reason
Sage's dispatch-preference change has room to win — but Sage's own occupancy ceiling is now the
limiting factor on how much further that lead can grow.
